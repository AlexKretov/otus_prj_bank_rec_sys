## 0. Резюме

**Что уже хорошо:**
- Завершённый сквозной пайплайн: EDA → предобработка → ALS-признак → sklearn Pipeline (OHE + scaler + feature selection + RF) → тюнинг Optuna → логирование в MLflow → FastAPI-сервис → нагрузочный прогон с отчётом.
- Осмысленный EDA с выводами после каждого раздела и итоговым аналитическим документом (`recommendations_analysis.md`).
- Все зависимости запинаны; `.env` и `data/` вынесены в `.gitignore`; секретов в репозитории нет (проверено).
- Есть артефакты для воспроизводимости предобработки: `replacer.json`, `columns.txt`, `feature_importances.csv`.

**Главные риски (по убыванию важности):**
1. Репозиторий в текущем виде **не собирается**: `requirements.txt` содержит маркеры merge-конфликта, `loader.ipynb` — невалидный JSON по той же причине, README задублирован.
2. Продовый сервис `app1.py` **не применяет часть предобработки** (результат `.map()` выбрасывается) и **не подтягивает персональные ALS-рекомендации** (lookup по позиционному индексу) — самый важный признак модели на проде фактически всегда `'0'`.
3. Целевая переменная сформирована **только по 3 продуктам из 24** (`range(3)` в `modeling.ipynb`), итоговые метрики в выводах **завышены** (precision 0.97 — это взвешенная метрика по классу «ничего не купил»; у целевого класса покупки precision 0.15).
4. Тюнинг гиперпараметров выполняется **по тестовой выборке** — заявленный ROC-AUC 0.9685 получен на тех же данных, на которых выбирались гиперпараметры.
5. `app.py` в закоммиченном виде **не запускается** (NameError, отсутствующий импорт, порча DataFrame).

## 3. Содержание: ML-методология (`modeling.ipynb`, `eda.ipynb`, `rec_sys.ipynb`)

1. **Целевая переменная покрывает 3 продукта из 24** (ячейка 24): `lambda row: [i+1 for i in range(3) if row[products[i]] == 1 ...]`. Учитываются только `ind_ahor_fin_ult1`, `ind_aval_fin_ult1`, `ind_cco_fin_ult1`. Это подтверждается `classification_report.txt`: классы «1» и «2» имеют support = **1**, класс «3» — 6005 при 275 тыс. негативов. Фактически система отвечает на вопрос «купит ли клиент текущий счёт», а не «какие продукты порекомендовать». Решить и зафиксировать в README: либо это осознанное сужение (тогда переписать формулировку задачи и выводы), либо `range(3)` → `range(len(products))` / осмысленный шорт-лист из EDA (продукты с долей >5%).
2. **Выводы о качестве завышены.** Markdown-вывод заявляет «высокую эффективность», «Precision 0.97», «2.2% ошибочных рекомендаций». Это взвешенные метрики, их делает класс «0» (доля ~98%). 3. **Тюнинг по тестовой выборке** (ячейка 52): `objective` делает `pipeline.fit(X_train, y_train)`, а скорит по `X_test` — Optuna дважды использует тест; итоговый ROC-AUC 0.9685 = максимум из перебора. 5. **Дисбаланс классов.** Классы 1 и 2 с 2–3 объектами на весь датасет делают `class_weight='balanced'` бессмысленным для них, а стратифицированный сплит — хрупким. Слить редкие таргеты в `'other'` или исключить, зафиксировав решение.

## 5. Тестирование (`test.ipynb`, отсутствие unit-тестов)

1. **«Нагрузочный» тест не нагружает** (ячейка 0): создаётся `ThreadPoolExecutor(max_workers=50)`, но запросы отправляются `send_request(url, df)` напрямую в цикле `while` — последовательно, ~1.8 RPS (в отчёте 92 запроса за 50 секунд успели). Executor не используется ни разу. Заменить на `executor.submit` + `as_completed` (или очередь фьючерсов с ограничением) — тогда 50 воркеров реально дадут нагрузку и p95/p99 обретут смысл.
2. Последняя ячейка дублирует тест с `max_time=505` — удалить или параметризовать (`max_time`, `workers`, `url` через переменные окружения/виджеты).
3. Полный `train_ver2.csv` читается, чтобы через `random.choice(df[col].unique())` собрать случайный профиль из несовместимых значений разных строк (возраст 116 + сегмент «UNIVERSITARIO»). Дешевле и честнее: взять 100 реальных строк датасета целиком (`df.sample(100, random_state=42).to_dict('records')`).
4. Критерий успеха — только HTTP 200. Добавить проверки схемы ответа (`prediction` — int из известного набора классов) и SLO по латентности, падение теста при нарушении.
5. **Unit/интеграционных тестов нет совсем.** Минимальный `pytest`-набор (без перестройки проекта):
   - golden-тest предобработки: один фиксированный вход → ожидаемый набор колонок/значений признаков;
   - `/predict`: happy path + битый запрос (нет `indrel`) → 422/понятная ошибка;
   - train/serve-согласованность: один и тот же клиент через ноутбучный пайплайн и через сервис → одинаковый вектор признаков (поймал бы почти все баги раздела 2);
   - smoke на артефакты: модель/`replacer.json`/`personal_als.parquet` грузятся, индекс parquet — `ncodpers`.
