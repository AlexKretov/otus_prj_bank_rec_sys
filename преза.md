## Слайд 1: Титульный слайд / Обзор проекта

### Заголовок
**Рекомендательная система банковских продуктов**  
*Промышленный контур ML: от исследовательского анализа до мониторинга микросервиса*

### Ключевая концепция
Разработка гибридной многоклассовой рекомендательной системы для клиентов банка Santander (Kaggle Dataset): предсказание следующего финансового продукта на основе социально-демографического профиля, истории владения продуктами и коллаборативной фильтрации.

### Полный жизненный цикл в репозитории
1. **Data Ingestion & EDA:** Загрузка 13.65M записей, анализ пропусков, аномалий и временных когорт (`loader.ipynb`, `eda.ipynb`).
2. **Feature Engineering & Modeling:** ALS-эмбеддинги, агрегаты, Optuna CV, Random Forest (`preprocessing.py`, `modeling.ipynb`).
3. **Offline Evaluation:** Временная валидация, расчет PR-AUC, Lift и ALS-метрик (`rec_sys.ipynb`, `artifacts/`).
4. **Production Service:** Микросервис FastAPI (`app1.py`), Docker Compose, Prometheus (`alerts.yml`), Grafana Dashboard.
5. **Quality Assurance & CI:** Нагрузочное тестирование (`load_test.py`, 50 workers, SLO p95 < 2.5s), мониторинг дрейфа PSI (`drift.py`), тесты pytest.

## Слайд 2: Постановка задачи и бизнес-контекст

### Формулировка ML-задачи
По историческому профилю клиента и набору открытых продуктов на конец 2015 года предсказать **первый продукт, который клиент откроет в 2016 году**.

### Структура целевой переменной (Target)
Задача сформулирована как **многоклассовая классификация с 14 взаимоисключающими классами**:
- **Класс `0` (`no_purchase`):** Покупки в 2016 году не было (**90.46%** выборки).
- **12 целевых классов шорт-листа:** Продукты с долей покупок $\ge 1\%$ в 2015 году:
  - `ind_recibo_ult1` (прямой дебет), `ind_cco_fin_ult1` (текущий счет), `ind_nomina_ult1` (зарплатный счет), `ind_ecue_fin_ult1` (электронный счет), `ind_cno_fin_ult1` (зарплатный аккаунт), `ind_tjcr_fin_ult1` (кредитная карта), `ind_reca_fin_ult1` (налоговый счет), `ind_nom_pens_ult1` (пенсионный счет), `ind_dela_fin_ult1` (длинный депозит), `ind_valo_fin_ult1` (ценные бумаги), `ind_ctop_fin_ult1`, `ind_ctpp_fin_ult1`.
- **Класс `99` (`other`):** Первым куплен редкий продукт вне шорт-листа (доля < 1%).

### Специфика данных и ограничения
- **Экстремальный дисбаланс:** 90.46% наблюдений — отсутствие покупки. Из оставшихся 9.54% большинство приходится на 3-4 ключевых продукта.
- **Бизнес-фокус:** Точность по продуктовым классам гораздо важнее общей accuracy. Главные метрики — **per-class PR-AUC** и **Lift относительно случайного предложения**.

## Слайд 3: Конвейер предобработки и хранение данных

### Архитектура хранения данных и артефактов
- **Сырые данные:** `data/train_ver2.csv` (13 647 309 строк, 48 колонок, ~2.14 ГБ). Загружаются через Kaggle API скриптом `loader.ipynb` (в Git не коммитятся).
- **Параметры предобработки:** `fastapi/preprocessing_params.json` — единый JSON со всеми вычисленными статистиками, квантилями, интервалами, агрегатами и эталонами дрейфа.
- **ALS-база:** `fastapi/personal_als.parquet` — быстрый lookup-справочник персональных рекомендаций по `ncodpers`.
- **MLflow Tracking:** `mlflow.db` (SQLite) + локальное хранилище артефактов (`classification_report.txt`, `feature_importances.csv`, `als_metrics.csv`).

### Модуль `preprocessing.py` — единый источник истины
Обучение (`modeling.ipynb`), офлайн-инференс (`rec_sys.ipynb`) и микросервис (`app1.py`) вызывают **один и тот же модуль**, что полностью устраняет **train-serve skew**.

### Пошаговый пайплайн (Train-Only Fit)
1. **Дроп неинформативных колонок:** Удаление `indrel`, `indext`, `nomprov` (дубликат `cod_prov`), `tipodom` (константа).
2. **Приведение типов и очистка:** Преобразование `age`, `antiguedad`, `renta` в float; замена маркера `-999999` в стаже на `NaN`.
3. **Импутация пропусков:** Медианы для числовых признаков, моды для категориальных (строго из `preprocessing_params.json`).
4. **Квантильный клиппинг:** Отсечение экстремальных выбросов `renta` [28 054; 309 371] и `antiguedad` [1; 207].
5. **Биннинг и когортизация:** Возраст разбивается на интервалы по кумулятивным продуктам (`age_interval`), даты (`fecha_alta`, `ult_fec_cli_1t`) — на квантильные когорты.
6. **Сворачивание редких категорий:** Категории с низкой частотой заменяются на `'other'` через `replacer.json`.
7. **Подсчет продуктового портфеля:** Сумма открытых продуктов `total_products`.

## Слайд 5: Выбор модели и методология обучения

### Выбранная архитектура модели
- **Модель:** `RandomForestClassifier(class_weight='balanced', random_state=0)`.
- **Sklearn Pipeline:**
  - `ColumnTransformer`: `StandardScaler` для числовых фичей + `OneHotEncoder(handle_unknown='ignore')` для категориальных.
  - `SelectFromModel`: Автоматический отбор наиболее значимых признаков вспомогательным ансамблем.
  - `RandomForestClassifier`: Финальный классификатор с балансировкой весов классов обратно пропорционально их частотам.

### Почему Random Forest + Class Weighting:
1. **Устойчивость к выбросам и нелинейным зависимостям:** Деревья решений естественно обрабатывают нелинейные финансовые признаки и дискретные интервалы.
2. **Эффективная работа с дисбалансом:** Параметр `class_weight='balanced'` штрафует ошибки на минорных классах (продуктах), заставляя модель учить редкие покупки.
3. **Надежность вероятностных оценок (`predict_proba`):** Позволяет формировать качественный Top-K список рекомендаций с калиброванными скорами уверенности.

### Подбор гиперпараметров (Optuna Optimization)
- **Фреймворк:** Optuna (алгоритм TPE Sampler).
- **Валидация:** 3-Fold `StratifiedKFold` строго внутри Train-выборки.
- **Целевая функция:** Macro ROC-AUC (OVR) по фолдам кросс-валидации.
- **Оптимальные параметры:**
  - `classifier__n_estimators`: **42**
  - `classifier__max_depth`: **10**
  - `classifier__min_samples_split`: **11**

## Слайд 7: Борьба с переобучением и устойчивость модели

### Комплекс мер по защите от переобучения

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                      СТРАТЕГИЯ ЗАЩИТЫ ОТ ПЕРЕОБУЧЕНИЯ                  │
├──────────────────────────┬─────────────────────────┬────────────────────┤
│   1. ВАЛИДАЦИЯ И СПЛИТ   │    2. РЕГУЛЯРИЗАЦИЯ     │ 3. PRODUCTION DRIFT│
├──────────────────────────┼─────────────────────────┼────────────────────┤
│ • Временной сплит по     │ • max_depth = 10        │ • Скользящее окно  │
│   fecha_alta (2013-10-09)│ • min_samples_split = 11│   (2000 запросов)  │
│ • Train-only fit для     │ • SelectFromModel       │ • Мониторинг PSI:  │
│   статистик и агрегатов  │ • class_weight='bal'    │   age, antiguedad, │
│ • 3-Fold Stratified CV   │ • Регуляризация ALS     │   renta            │
│ • Тест трогается 1 раз   │   (reg=0.05)            │ • Алерт PSI > 0.25 │
└──────────────────────────┴─────────────────────────┴────────────────────┘
```

1. **Честный Temporal Split:**
   - Разбиение по дате привлечения `fecha_alta` (Train: 644 744 до cutoff; Test: 275 674 после cutoff).
   - *Почему не дата среза `fecha_dato`:* клиенты с ранним последним срезом — это ушедшие из банка клиенты (утечка и смещение таргета к 0).
2. **Исключение Data Leakage:**
   - Все статистики (медианы, квантили, когорты, групповые средние) вычислены **только на train**.
   - Невиданные категории маппятся в `__default__` или `'other'`.
3. **Структурная регуляризация:**
   - Ограничение глубины (`max_depth=10`) и размера листа (`min_samples_split=11`) устраняет заучивание обучающей выборки.
   - Фильтрация зашумленных признаков через `SelectFromModel`.
4. **Data Drift Monitoring на проде (`drift.py`):**
   - Расчет Population Stability Index (PSI) для входных признаков относительно эталона.
   - Prometheus Alert `BankRecommenderFeatureDrift` при PSI > 0.25.

## Слайд 8: План vs Факт, причины отклонений и Production-контур

### Сопоставление первоначального плана и итоговой реализации

| Направление | Что планировалось | Что получилось на самом деле | Причины изменений и инженерное решение |
|---|---|---|---|
| **Модель** | Чистая матричная факторизация (ALS) для 24 продуктов | **Двухуровневая гибридная модель:** ALS-признак + Random Forest на 14 классов | Чистый ALS давал Hit Rate всего 13.4% и не учитывал демографию; продукты <1% объединили в `other` |
| **Схема сплита** | Случайный K-Fold / Random Train-Test Split | **Временное разбиение по `fecha_alta`** | Случайный сплит давал завышенные метрики (data leakage); сплит по `fecha_dato` смещал train к оттоку |
| **Feature Engineering** | Использование Featuretools DFS в runtime | **Векторизованный numpy/pandas в `preprocessing.py`** | Featuretools DFS в runtime добавлял 50-100 мс на запрос; ручной векторизованный код снизил задержку до <2 мс |
| **Инфраструктура** | Простой Jupyter-ноутбук | **Полноценный Production-стек:** FastAPI + Prometheus + Grafana + Docker | Необходимость соответствия SLO по нагрузке, мониторинга доступности, задержки и дрейфа данных |

### Результаты нагрузочного тестирования микросервиса (`load_test.py`)
- **Нагрузка:** 50 параллельных воркеров, 1 408 запросов.
- **Success Rate:** **99.01%** (SLO $\ge 99.0\%$, все 14 ошибок — валидируемые HTTP 422 некорректных профилей).
- **Латентность:** Avg = 1 822 мс, **p95 = 2 483 мс** (SLO p95 < 5 000 мс), p99 = 2 671 мс.
- **Производительность:** **27.56 RPS** на одном инстансе.
